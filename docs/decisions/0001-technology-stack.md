# Creator 技术栈决策

日期：2026-09-13

状态：已被 [0002：细结构重建技术栈](0002-reconstruction-stack.md) 取代。以下保留旧场景生成方向的历史记录，不再作为当前实现要求；其中的环境检查也仅代表当时的检查范围。

## 目标与约束

Creator 从自然语言需求和实际 3D 资产生成可检查的室内场景，支持有限的移动、转向编辑。研究假设是：在相同模型、布局器和视觉观察预算下，根据资产方向识别错误对场景任务的影响分配观察机会，可以减少最终摆放错误。该假设仍须由先导实验验证。

首版范围是静态单房间、已确认尺度与直立姿态的资产。主要研究变量是水平正面方向的观察分配。安装规则、渲染设置和布局器作为共享条件。当前设备为 Windows、RTX 4060 Laptop GPU、8188 MiB 显存。资产数量不能单独决定渲染负载，还需控制网格复杂度和纹理大小。

现有 C++/OpenGL 项目保留为历史原型。重建不以复用旧架构为前提。本次只新增决策文档，不修改旧实现。

## 核心决定

采用独立 Python 研究核心，加 Blender 资产/渲染适配层。先完成命令行闭环，再添加 Blender 插件作为交互入口。

- 核心：Python 3.11，独立虚拟环境，使用 uv 管理并锁定依赖。
- 场景表示：Pydantic 2 定义和校验 Scene IR；JSON 保存状态，JSONL 保存实验事件。结构校验不等于几何或语义正确性。
- 几何：NumPy、trimesh；Shapely 用于水平占地和通行区域；python-fcl 作为细碰撞检查的首选后端。后端须通过实际安装及几何用例验证，不把包围盒相交直接当作实体碰撞。
- 布局：以 PyTorch 实现/承载选定基线的可微约束优化；首版只维护一套主要求解路径。观察调度不强制使用 GPU，也不为使用深度学习而添加训练任务。
- 渲染和资产工具：Blender 4.5 LTS 系列，首次验证目标为官方当前列出的 4.5.13。4.5 LTS 支持至 2027 年 7 月；这是主动选择一个固定基线，并非声称它是最新 LTS。
- 渲染器：EEVEE 作为首选观察图和交互预览渲染器，固定相机、灯光、背景、色彩管理和分辨率。Cycles 仅在需要时用于展示图，不混入主实验造成不公平条件。
- 交互：后续 Blender 薄插件，负责需求输入、发起任务、查看进度、加载结果、显示方向和约束；算法和 API 调用保留在独立核心。
- 交换格式：GLB 保存资产，JSON 保存权威场景与任务状态；PNG 保存观察图；必要的几何数组可使用 NPZ。BLEND 是查看与展示产物，不是唯一数据来源。
- 验证：pytest 覆盖关键坐标变换、约束、几何反例和小规模端到端流程；实验保留输入、版本、种子、模型响应和成本。

除上述明确选择的版本系列外，具体依赖版本在首轮兼容性验证后写入锁文件。未执行安装意味着当前不能声称这些依赖组合已经在本机通过测试。

## 进程边界与执行方式

普通 Python 核心持有 Scene IR、观察历史、布局算法和评测逻辑。Blender 接收任务及资产文件，完成导入、渲染、场景构造与导出。

第一阶段使用任务 JSON、输出目录、日志及进程退出码连接两者。Python 调用 Blender 后台批处理；一个任务批次处理多资产或多视图，避免每张图片重启一次 Blender。无需常驻网络服务、WebSocket、数据库或消息队列。

计算流程：

1. 导入并标准化资产，输出可计算的几何、变换记录与可渲染资产。
2. Blender 渲染初始视图；核心处理视觉模型响应，保留方向候选。
3. 核心生成暂定布局，估计方向歧义对任务的影响。
4. 核心选择下一个观察资产；Blender 按预设视角序列补充出图。
5. 核心更新判断并求解，在独立几何检查后输出 Scene IR。
6. Blender 读取结果生成可查看、可编辑的场景。

优化迭代在普通数组和张量中进行，不在每一步读写 Blender 场景对象。渲染和求解之间交换数据，而不是把 Blender UI 当作控制接口。

插件阶段复用相同任务入口。API 等待和求解在外部进程运行，Blender 场景更新通过主线程执行。避免长期后台 Python 线程操作 bpy。初版 GPU 渲染任务串行执行；增加并发或常驻工作进程须由测量结果支持。

## 数据与实验约定

- Scene IR 使用米和明确的右手坐标约定，内部采用 Z 轴向上；glTF 导入导出的坐标转换仅在适配边界处理并验证。
- 模型局部正面方向与场景世界旋转分开存储。文件轴约定不等于已识别物体语义正面。
- 原始资产不覆盖；派生资产、网格哈希、处理版本和变换记录可追踪。
- 缓存键包含资产内容、相机、渲染设置和版本；视觉响应缓存另含模型与提示词标识。
- 缓存存在不代表算法已经观察到对应图像。实验记录每种策略实际获得的视图与模型响应；重放实验与实时调用成本分开报告。
- 相同任务的对照方法共享资产、尺度、初始视图、布局器和总观察预算。人工方向真值保留用于评测，不进入待测算法。
- Blender 中的临时人工操作不自动成为核心状态；受支持编辑须形成 Scene IR 变更，再校验并更新场景。首版不承诺任意双向编辑同步。
- 几何检查和语义方向评测分开。视觉终审如果使用，也计入观察成本，不能当作人工真值。

## 备选方案的结论

| 方案 | 首版结论 | 重新考虑的条件 |
| --- | --- | --- |
| 重建 C++/OpenGL 独立编辑器 | 不采用为主线。它需要额外承担资产、材质、相机、交互和导出工作。 | 有经过测量的轻量查看器需求，且现成宿主不能满足。 |
| 自写 Vulkan 渲染器 | 不采用。当前研究不需要自行控制底层图形资源与同步。 | 研究问题转为 GPU 渲染、图形调度或明确的渲染吞吐瓶颈。 |
| Blender 内部单体插件 | 不采用。插件保留为界面，研究核心独立。 | 任务退化为少量同步资产操作且不需要独立实验运行。 |
| UE5 编辑器插件 | 暂缓。可以实现，但当前没有必须依赖 UE 的需求。 | 明确需要 UE 关卡交付、运行时角色交互或具体 UE 仿真集成。 |
| 独立 Python 核心 + Blender | 采用。资产、渲染与研究计算各有明确边界。 | 首轮验证暴露无法在预算内解决的阻塞，再复议具体组件。 |

OpenGL/Vulkan 是图形 API，Blender/UE 是包含资产、编辑和渲染工具的宿主，不是同一层面的四种库。Blender 内部采用哪种图形后端不作为本项目原创工作或算法变量；运行环境与后端设置需要记录。

UE 官方 Python 支持限于 Editor，不能直接当作 PIE、Standalone 或打包程序中的玩法脚本。UE 编辑器插件可以满足编辑器内使用，但独立应用需要另外设计运行时。

## 首轮技术验证

先选 3–5 个具有纹理、复杂节点变换或不同结构的真实资产，不以简单立方体代替全部输入。完成：

1. 在隔离环境中安装核心依赖并运行基础几何检查；确认 Blender 精确版本。
2. Python 驱动 Blender 后台导入并批量渲染预设视图，验证材质、相机和坐标一致性。
3. 从几何信息构造一个最小场景，核心求解后写回 Blender；核对显示结果与数值检查一致。
4. 验证实体相交、正常接触和椅子伸入桌底等情况，明确碰撞与支撑检查的能力边界。
5. 修改一个对象的目标位置或方向，重新求解并导出；验证稳定对象 ID 和场景状态可追踪。
6. 重新打开导出场景，记录失败、总耗时、批量渲染耗时和显存占用。

通过后锁定 Blender 补丁版本和核心依赖。公开论文基线如有不同依赖，使用独立环境按其要求复现，不强行并入核心环境。Windows 原生先完成主闭环，Linux/WSL 仅在具体基线需要时引入。
